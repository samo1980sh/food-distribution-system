# Dynamic Phase 3E-1 — عقد عمليات السائق الميدانية المتقاعد

> **الحالة: RETIRED / HISTORICAL COMPATIBILITY**
>
> هذا المستند يصف عقدًا تاريخيًا لم يعد متاحًا كمسار تشغيل حالي. أزيلت
> مسارات Driver المستقلة من Laravel وتطبيق Flutter. دورة العمل الحالية
> موحدة تحت دور `sales_representative` باستخدام `SalesJourney` والتسليم
> الفوري للفواتير. تبقى بيانات `DriverJourney` و`DriverDelivery` القديمة
> للحفظ التاريخي والمصالحة والتوافق مع عمليات المزامنة المتقادمة فقط.

## الهدف

إضافة سجل رسمي لرحلة السائق ونتائج التسليم فوق الفواتير المعتمدة الموجودة،
دون تكرار منطق الفواتير أو المخزون أو المرتجعات.

## القرار المعماري

لم يكن في Laravel أي كيان لرحلة السائق أو إثبات التسليم. وكانت شاشات
Flutter الخاصة بالتسليم والمصاريف واجهات Presentation تجريبية فقط.

لذلك أضيفت ثلاثة جداول رسمية:

- `driver_journeys`
- `driver_deliveries`
- `driver_delivery_items`

## دورة العمل التاريخية

1. `open-today` يفتح رحلة اليوم ويأخذ Snapshot للفواتير المعتمدة التابعة
   للخط والسيارة والمستودع.
2. لا تبدأ الرحلة قبل استلام أوامر التحميل المعتمدة.
3. يسجل السائق نتيجة كل فاتورة: كامل، جزئي، أو فاشل.
4. الكمية المسلمة + الكمية المرتجعة يجب أن تساوي الكمية المتوقعة لكل مادة.
5. لا تنتهي الرحلة قبل معالجة جميع التسليمات.
6. كل إجراء يدعم REST المباشر وPush Batch مع `base_version`.
7. تغيّر نتيجة التسليم يحدّث نسخة الرحلة أيضاً حتى تصل ملخصات التسليم
   الصحيحة عبر Pull. ويُعامل إنهاء الرحلة كعملية قابلة للدمج مع تغييرات
   أبنائها ضمن الدفعة Offline نفسها، مع بقاء حارس الحالة والتسليمات المعلقة.

## اتساق العمليات المرتبطة

- الفاتورة المعتمدة أثناء رحلة جاهزة أو جارية تدخل فوراً في قائمة التسليم.
- لا يمكن اعتماد فاتورة جديدة بعد اكتمال رحلة اليوم.
- يمكن إلغاء فاتورة مرتبطة فقط قبل بدء الرحلة، وعندها يحذف Snapshot المعلق.
- عند وجود رحلة، لا يقبل جرد الإقفال اليومي قبل اكتمالها.
- يبقى السلوك السابق متاحاً للسجلات القديمة التي لا تملك رحلة.

## المرتجعات والمخزون

الكمية المرتجعة في نتيجة التسليم هي **إثبات ميداني مادي** فقط. لا تنشئ
حركة مخزون ولا مستند مرتجع تلقائياً. يبقى مستند `sales_return` الحالي هو
المسار المالي والمخزني الرسمي، وبذلك لا يتكرر أثر المخزون ولا تتوسع صلاحية
السائق لإنشاء مرتجعات مالية.

## إثبات التسليم

يدعم العقد:

- اسم المستلم.
- هاتف المستلم اختيارياً.
- ملاحظة الإثبات.
- الموقع الجغرافي اختيارياً.
- سبب الفشل.
- تفاصيل الكميات لكل مادة.

رفع الصور والتوقيع غير داخل هذه المرحلة لأن ملفات Offline تحتاج قناة رفع
مستقلة؛ لا يتم ادعاء دعمها قبل تنفيذ ذلك بشكل آمن.

## المسارات التاريخية المتقاعدة

المسارات التالية غير مسجلة حاليًا ولا تمثل API مدعومًا:

```text
POST /api/v1/operational/driver-journeys/open-today
GET  /api/v1/operational/driver-journeys/{driverJourney}
POST /api/v1/operational/driver-journeys/{driverJourney}/start
POST /api/v1/operational/driver-journeys/{driverJourney}/finish
GET  /api/v1/operational/driver-deliveries/{driverDelivery}
POST /api/v1/operational/driver-deliveries/{driverDelivery}/submit-outcome
```

## المزامنة التاريخية

كانت عمليات Push Batch القديمة تستخدم:

```text
driver_journeys / start
driver_journeys / finish
driver_deliveries / submit_outcome
```

لا يعرض Pull أو Bootstrap الحالي `driver_journeys` أو `driver_deliveries`.
تُحفظ تواقيع Push القديمة مؤقتًا حتى تُرفض العمليات المتقادمة بصورة
حتمية عبر `representative_driver_workflow_retired` بدل فشل تفسير الدفعة.

## المصاريف والمرتجعات الرسمية

- مصاريف السيارة تستمر عبر عقد `vehicle_expenses` الحالي ضمن مساحة عمل
  المندوب الموحدة، مع إبقاء مصدر السائق القديم قابلًا للقراءة تاريخيًا.
- نتيجة التسليم تحفظ الدليل الميداني فقط. إنشاء المرتجع الرسمي يبقى عبر
  `sales_returns` لمندوب المبيعات أو الإدارة وفق الصلاحيات الحالية.
